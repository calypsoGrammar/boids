# CAL-1482: spatial grid for neighbour search

Ticket: a spatial grid for neighbour search, with the slider maximum kept at
200 and no change in behaviour. Agreed target: the grid gives the same
neighbour sets and simulation results as all-pairs (checked by tests), and
`stress-1000` is at least 3x faster than the ~90-100 ms per tick recorded in
`BOIDS-V1-06.md` §5.

## Change

- `Step()` calls `BuildGrid()` once per tick for flocks of 64 or more agents
  (`GRID_MIN_AGENTS`). Agents are bucketed into square cells at least as wide
  as the largest vision, and `GetNearbyAgentsGrid()` tests only the 3 x 3 cells
  around an agent.
- Each occupied cell sorts its candidates once, ascending, so every `nearby`
  and `close` list has the same agents in the same order as all-pairs. The sums
  in `Steer()` therefore add in the same order and the results are bit-for-bit
  the same.
- The grid's buffers live on the flock and are regrown only when the flock or
  the cell count grows, so the search and steering allocate nothing (the point
  of §5 of the V1-06 note). `Step()` still makes a small edges object per tick.
- Flocks with a vision that is not a finite positive number, or an agent with
  `x = NaN` (which all-pairs lets through its x test), are searched all-pairs.
- `GetNearbyAgents()` is unchanged and is the reference the tests compare to.
- `Steer()` sums alignment and cohesion in one pass over the neighbours, with
  one weight, and skips the division for same-species neighbours (dividing by
  1 changes nothing). Each sum adds in the same order, so results are the same.
- Agents of a species share one colour string object (`InternColour`), so the
  per-neighbour species test in `Steer()` is by identity, not by comparing the
  text. This was the largest single saving after the grid itself.
- `Step()` works out the box edges once per agent radius and passes them to
  `DetectEdgeCollisions()`, instead of allocating two arrays per agent.
- `Coefficient()` reads the offset name from `COEFFICIENTS` instead of building
  it by string concatenation, and no longer destructures an array.

## Checks

`test/grid.test.js` compares grid and all-pairs neighbour lists over 20 ticks
of three flocks, with lost, infinite and coincident agents, and compares 50
ticks of `Step()` with and without the grid. The bench checksums are the same
before and after for all six scenarios.

The slider range did not regress on the final code; every scenario is faster or within noise.

## Ratio against the 3x target

On this machine `stress-1000` is 2.6-3.1x faster than base (pairing the runs
above; 2.7x on the medians). That is close to, but not reliably at, 3x.
Measured against the 88-103 ms per tick recorded on the 2-vCPU runner in
`BOIDS-V1-06.md` §5, the branch is about 14x faster, but the two figures come
from different machines, so that is not a measured ratio. This machine runs the
base at 16-19 ms, not 88-103 ms. Re-running `npm run bench -- stress-1000` on
the original runner would give the real ratio; which baseline counts is the
owner's decision.

Profile of `stress-1000` on the final code (self time, whole bench run,
`node --cpu-prof`): `SteerAllGrid` 444 ms (neighbour filtering and steering
are now one function), `BuildGrid` 113 ms, canvas calls 75 ms, garbage
collection 74 ms, `Step` 57 ms. This run covers more than the 100 ticks of the
first profile, so the totals are not comparable with it; the `Steer` result
arrays are no longer a garbage source. Cells of half a vision with a 5 x 5
search were tried in attempt 1 and were no faster, so they were not kept.

## Attempt 2 and review repair: allocation and read-pattern savings

All changes keep the checksums (`b55fa070c79b6e78` for `stress-1000`, and the
other five equal to base) and the grid-versus-all-pairs tests.

1. `GetNearbyAgentsGrid` overwrites the neighbour lists by index and sets
   `length` once at the end instead of `length = 0` and `push`.
2. `Step` steers through `SteerInto(agent, out)`, which writes into a reused
   `Float64Array(2)`; `Steer` still returns `[x, y]` for `Adjust` and tests.
3. `BuildGrid` snapshots `x`, `y`, `vx`, `vy` and a species number per agent,
   and stores each candidate's x and y in `fx`/`fy` aligned with `found`.
4. With the grid, `Step` calls `SteerAllGrid`, which reads the grid fields once,
   filters with sequential reads of `fx`/`fy`, and steers from the typed
   snapshots, comparing species numbers; it touches no neighbour agent objects.
   The all-pairs path and `Steer`/`SteerInto` read agent objects as before.

Gains, measured against the previous commit with alternating runs of
`stress-1000` (medians of `msPerTick`):

| Change | Previous | After | Reading |
| --- | --- | --- | --- |
| 1 and 2 (against `351adb5`, 5 runs) | 20.28 | 7.41 | the 2.7x of attempt 1's note; their separate parts were not isolated |
| 3, aligned `fx`/`fy` (6 runs) | 6.73 | 5.96 | about 0.7 ms (11%), within the noise but in the same direction in most pairs |
| 4, `SteerAllGrid` with species numbers and typed reads (10 runs, three-way) | 5.95 | 6.19 | no gain visible; minimums 4.99 against 4.84 |

Change 4 therefore gave nothing measurable on this machine; it is
bit-identical and kept, but it duplicates the steering sums of `SteerInto`, and
the owner may prefer to drop it for less code.

Final three-way run (10 alternating runs, `msPerTick`): base 14.7-32.2 (median
17.1), previous commit 5.0-10.6 (median 5.95), final 4.8-9.5 (median 6.19).
The final median ratio against `351adb5` is about 2.8x (best-case pairs and
the minimums give 3x or more; the worst give 2x). It is not reliably 3x on a
same-machine reading, and no behaviour was changed to reach it. Which baseline
counts (F4) remains the owner's decision.
