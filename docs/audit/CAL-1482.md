# CAL-1482: spatial grid for neighbour search

Ticket: a spatial grid for neighbour search, with the slider maximum kept at
200 and no change in behaviour. Agreed target: the grid gives the same
neighbour sets and simulation results as all-pairs (checked by tests), and
`stress-1000` is at least 3x faster than the ~90-100 ms per tick recorded in
`BOIDS-V1-06.md` §5.

## Change

- `Step()` calls `BuildGrid()` once per tick for flocks of 64 or more agents
  (`GRID_MIN_AGENTS`). Agents are bucketed into square cells at least as wide
  as the largest vision, and `GetNearbyAgentsGrid()` tests only the 3 x 3 cells
  around an agent.
- Each occupied cell sorts its candidates once, ascending, so every `nearby`
  and `close` list has the same agents in the same order as all-pairs. The sums
  in `Steer()` therefore add in the same order and the results are bit-for-bit
  the same.
- The grid's buffers live on the flock and are regrown only when the flock or
  the cell count grows, so the search and steering allocate nothing (the point
  of §5 of the V1-06 note). `Step()` still makes a small edges object per tick.
- Flocks with a vision that is not a finite positive number, or an agent with
  `x = NaN` (which all-pairs lets through its x test), are searched all-pairs.
- `GetNearbyAgents()` is unchanged and is the reference the tests compare to.
- `Steer()` sums alignment and cohesion in one pass over the neighbours, with
  one weight, and skips the division for same-species neighbours (dividing by
  1 changes nothing). Each sum adds in the same order, so results are the same.
- Agents of a species share one colour string object (`InternColour`), so the
  per-neighbour species test in `Steer()` is by identity, not by comparing the
  text. This was the largest single saving after the grid itself.
- `Step()` works out the box edges once per agent radius and passes them to
  `DetectEdgeCollisions()`, instead of allocating two arrays per agent.
- `Coefficient()` reads the offset name from `COEFFICIENTS` instead of building
  it by string concatenation, and no longer destructures an array.

## Checks

`test/grid.test.js` compares grid and all-pairs neighbour lists over 20 ticks
of three flocks, with lost, infinite and coincident agents, and compares 50
ticks of `Step()` with and without the grid. A further test advances two
identically seeded flocks of 150 agents (three species, bias 4, wrap and turn)
through `Step()`, one with `BuildGrid` stubbed to false, and compares `nearby`,
`close`, `x`, `y`, `vx`, `vy` and `outBox` after every tick. It includes NaN,
infinite, far-off and coincident agents and a canvas shrunk mid-run, so agents
go off canvas and keep their stale lists. Making the off-canvas branch of
`GetNearbyAgentsGrid` clear the lists makes it fail. The bench checksums are
the same before and after for all six scenarios.

## Ratio against the 3x target

On this machine, final code, eight alternating runs, `stress-1000` runs at a
median of 5.8 ms per tick against 19.4 ms for `351adb5`: about 3.4x (the
minimum, 4.6 ms, against the base median is 4.2x; one slow run at 12.7 ms gives
1.5x). Earlier measurements of the same design gave 2.7-2.8x with the machine
in a noisier state, so the ratio varies by about +-0.5x between sessions and is
not reliably at or above 3x. Measured against the 88-103 ms per tick recorded
on the 2-vCPU runner in `BOIDS-V1-06.md` §5, the branch is about 14x faster,
but the two figures come from different machines, so that is not a measured
ratio. This machine runs the base at 15-22 ms, not 88-103 ms. Re-running
`npm run bench -- stress-1000` on the original runner would give the real
ratio; which baseline counts is the owner's decision.

Profile of `stress-1000` on the final code (self time, whole bench run,
`node --cpu-prof`): `GetNearbyAgentsGrid` 263 ms, `SteerInto` 90 ms,
`BuildGrid` 88 ms, canvas calls 61 ms, garbage collection 58 ms, `Step` 46 ms.
The `Steer` result arrays are no longer a garbage source. Cells of half a
vision with a 5 x 5 search were tried in attempt 1 and were no faster, so they
were not kept.

## Attempt 2 and review repairs: allocation and read-pattern savings

All changes keep the checksums (`b55fa070c79b6e78` for `stress-1000`, and the
other five equal to base) and the grid-versus-all-pairs tests.

1. `GetNearbyAgentsGrid` overwrites the neighbour lists by index and sets
   `length` once at the end instead of `length = 0` and `push`.
2. `Step` steers through `SteerInto(agent, out)`, which writes into a reused
   `Float64Array(2)`; `Steer` still returns `[x, y]` for `Adjust` and tests.
3. `BuildGrid` snapshots `x` and `y` and stores each candidate's x and y in
   `fx`/`fy` aligned with `found`, so the filter reads them in sequence.

Tried and removed: a `SteerAllGrid` that merged the search and steering, read
neighbour `vx`, `vy` and a species number from typed snapshots and read the
grid fields once. Its median was 6.19 ms against 5.95 ms without it (10 runs),
so it gave nothing measurable; it also kept a second copy of the filter and
the steering sums that the tests did not cover, so it was removed. `Step` runs
one search path, `GetNearbyAgentsGrid`, then `SteerInto`.

Gains, `stress-1000`, medians of `msPerTick` from alternating runs:

| Change | Previous | After | Reading |
| --- | --- | --- | --- |
| 1 and 2 (against `351adb5`, 5 runs) | 20.28 | 7.41 | 2.7x; their separate parts were not isolated |
| 3, aligned `fx`/`fy` (6 runs) | 6.73 | 5.96 | about 0.7 ms (11%), within the noise but in the same direction in most pairs |
| `SteerAllGrid` (10 runs, removed) | 5.95 | 6.19 | no gain |
| Final code (8 runs, against `351adb5`) | 19.4 | 5.8 | about 3.4x |

No behaviour was changed to reach the ratio. The final figure is above 3x in
this session, but earlier sessions on the same code family read 2.7-2.8x, so
which baseline and which reading counts (F4) remains the owner's decision.
